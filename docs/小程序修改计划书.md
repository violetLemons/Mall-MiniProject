# 小程序修改计划书（水果商城改造）

> 需求来源：`docs/小程序修改需求.md`
> 目标：将当前「通用商城」改造为主要售卖水果（并保留其他品类商品）的项目，按需求逐条落地，**最小改动、不删功能、宁多勿少**。
> 本计划按依赖关系做拓扑排序：数据层 → 后端云函数 → 前端服务层 → 前端页面 → PC 管理后台 → 联调验证。同一阶段内无强依赖的任务可并行。

---

## 〇、现状核对结论（改造前基线）

| 需求点 | 现状 | 结论 |
| :--- | :--- | :--- |
| #2 菜单导航顺序：首页、分类、客服、购物车、我的 | `app.json` tabBar 仅 4 项：首页/分类/购物车/我的，无「客服」 | **需新增客服页 + 调整 tabBar 顺序** |
| #3 首页逻辑与布局保持一致 | 首页 = 自定义导航 + 搜索 + 轮播 + 金刚区 + 双列商品流 | **保持不变，仅需微调金刚区数据源** |
| #4 首页上半部分轮播图，下方两列商品 | 已实现（swiper 轮播 + product-grid 双列） | **已满足，回归即可** |
| #5 分类两级词条（左主类 → 右次类 → 出商品） | 分类为**单层**：`categories` 无 `parentId`，`products.categories` 返回扁平数组 | **需实现两级分类（前后端+库）** |
| #6 我的订单 5 项 + 进列表后多「待评价/已完成」 | 我的页订单宫格仅 4 项（待付款/待发货/待收货/售后退款）；订单列表页仅 4 个 tab | **需调整订单宫格与订单列表 tab** |
| #7 激活卡密功能 | 无任何卡密/兑换功能与表 | **需从零实现（表+云函数+页面）** |
| #8 其余功能不改、不删 | 收藏/足迹/地址/优惠券占位/设置/支付/自提等均存在 | **保留，确保兼容** |

**关键既有事实（改造时依赖）：**
- 订单状态机（`merchant_orders.status`）：`PENDING_PAYMENT → PAID → SHIPPED → COMPLETED`，另有 `WAITING_PICKUP / READY_FOR_PICKUP`、`CANCELLED`、退款态 `REFUND_PENDING`（后端 `orders.applyRefund` 写入）与前端 `OrderModel` 里出现的 `REFUNDING / REFUNDED`（命名不统一，需梳理）。
- 商品按 `categoryId` 归属分类；首页金刚区与分类页共用 `CategoryService.getQuickCategories()`（需拆分为「一级分类」与「完整树」两套）。
- `assets/icons/` 现有 home/category/cart/profile/discover 五组图标，其中 **discover 未被使用**，无「客服」图标。
- 本地网关 `127.0.0.1:3001`（`scripts/local-admin-api.js`）与云端 `wx.cloud.callFunction` 双通道，改造后需两者契约一致。

## 二、阶段 1：数据层（数据库 Schema 与演示数据）

> 说明：本阶段只改「表结构定义、建表/建集合脚本、种子演示数据」，不写业务逻辑，是全项目的地基。

### T1.1 数据库结构扩展设计
- **目标**：确定三个数据结构的最终字段。
- **改动点**：
  1. `categories` 增加 `parentId`（空字符串/null = 一级分类；否则为所属一级分类 `_id`），用于两级分类。
  2. `merchant_orders` 增加 `reviewed: Boolean`（默认 `false`），用于区分「待评价 / 已完成」。
  3. 新增集合 `activation_codes`（卡密表），字段建议：
     - `code`（卡密，唯一）、`status`（`UNUSED / USED / DISABLED`）、`type`（权益类型）、`benefit`（权益内容/数值）、`createdAt`、`redeemedBy`（兑换用户 openid）、`redeemedAt`。
  4. 新增集合 `activation_records`（兑换流水，可选，便于审计）：`code`、`userId`、`benefit`、`createdAt`。
- **依赖**：无（纯定义）。
- **验收**：字段定义与「数据库」一节一致，可供阶段 2/3 引用。

### T1.2 更新 `docs/database-schema.md`
- **目标**：文档与库结构保持一致。
- **改动点**：补充 `categories.parentId`、`merchant_orders.reviewed`、新增 `activation_codes` / `activation_records` 集合说明与索引建议（`activation_codes.code` 唯一索引）。
- **依赖**：T1.1。
- **验收**：文档字段表、索引清单已同步。

### T1.3 更新 `cloudfunctions/initDb/index.js`
- **目标**：建集合脚本纳入新集合，并把演示分类/商品换成「水果为主 + 其他品类」的两级结构。
- **改动点**：
  1. `COLLECTIONS` 数组加入 `activation_codes`、`activation_records`。
  2. `DEMO_CATEGORIES` 改为两级：一级（如「新鲜水果」「进口水果」「坚果零食」等，`parentId` 为空），二级（如「苹果」「香蕉」「柑橘」「浆果」「热带水果」等，`parentId` 指向一级）。
  3. `DEMO_PRODUCTS`/`DEMO_SKUS` 更换为水果类演示商品，`categoryId` 指向**二级**分类。
  4. 增加演示卡密（如 `DEMO-CODE-001`）供兑换测试。
- **依赖**：T1.1。
- **验收**：重跑 `initDb` 可幂等建集合并灌入两级分类水果演示数据。

### T1.4 更新 `scripts/seed-demo-data.js`（及必要时 `scripts/init-db.js`）
- **目标**：本地/脚本演示数据与云函数一致。
- **改动点**：同步 T1.3 的两级分类、水果商品、演示卡密；`scripts/init-db.js` 若有集合清单也同步加新集合。
- **依赖**：T1.1。
- **验收**：脚本导出的数据字段与新 schema 完全一致。

## 三、阶段 2：后端云函数

> 说明：依据阶段 1 的数据结构，提供前端所需契约。

### T2.1 `products` 云函数：分类两级返回
- **目标**：让前端能拿到「一级 + 二级」分类树。
- **改动点**（`cloudfunctions/products/index.js` 的 `categories` action）：
  1. 查询结果透传 `parentId` 字段。
  2. 新增/调整返回值：既保留扁平数组（含 `parentId`），也返回 `tree`（一级分类，内嵌 `children` 二级数组），或前端自行分组（推荐后端直接返回树，前端更简单）。
- **依赖**：T1.1 / T1.3。
- **验收**：调用 `products.categories` 可区分一级/二级；首页金刚区取一级，分类页取整树。

### T2.2 `products` 云函数：`list` 按二级分类筛选兼容
- **目标**：确认/补强按二级分类 `categoryId` 精确过滤。
- **改动点**：现有 `list` 已按 `params.categoryId` 精确匹配；若有二级分类归属多个分类的情况，确认 `categoryId` 指向二级即可，无需大改。若需「按一级分类聚合所有二级商品」，增加 `parentCategoryId` 参数支持。
- **依赖**：T2.1。
- **验收**：分类页选中二级分类后能返回对应水果。

### T2.3 `adminCategories` 云函数：分类支持 `parentId`
- **目标**：后台可创建/维护两级分类。
- **改动点**（`cloudfunctions/adminCategories/index.js`）：
  1. `create`/`update` 支持 `parentId` 字段。
  2. `list` 返回 `parentId`，并支持返回树形（或前端按 `parentId` 分组）。
  3. `delete` 外键校验扩展：一级分类下存在二级子类或商品时禁止删除。
- **依赖**：T1.1。
- **验收**：后台可建一级/二级分类，删除保护正确。

### T2.4 `orders` 云函数：`list` 支持组合状态过滤
- **目标**：支撑订单列表页新 tab（退款中 / 待评价 / 已完成 / 全部）。
- **改动点**（`cloudfunctions/orders/index.js` 的 `list` action）：
  1. 支持组合状态 token（如 `REFUND` → `REFUND_PENDING|REFUNDING|REFUNDED`；`PENDING_REVIEW` → `status==COMPLETED && reviewed!=true`；`COMPLETED` → 已完成）。
  2. 保持现有 `status` 单值过滤兼容。
- **依赖**：T1.1（`reviewed` 字段）。
- **验收**：传入各 tab 的 token 能返回正确子集且分页正确。

### T2.5 新增 `activation` 云函数（卡密兑换）
- **目标**：实现卡密「校验 + 兑换 + 落流水」。
- **改动点**：新建 `cloudfunctions/activation/`（遵循现有 `common/` 复制模式，`package.json`/`config.json`/`index.js` 齐备），提供：
  1. `redeem`：校验 `code` 存在且 `UNUSED` → 原子置 `USED`、绑定 `redeemedBy`、写 `activation_records`、返回权益结果。
  2. `generate`（管理端）：批量生成卡密（鉴权走 `adminAuth` 或仅管理员可调）。
  3. 幂等与并发防重（同一卡密只允许兑换一次）。
- **依赖**：T1.1 / T1.3（集合存在）。
- **验收**：卡密可兑换一次、二次兑换被拒、流水正确；`bundle-functions.js` 能正常打包该函数。

### T2.6 统一退款状态命名
- **目标**：消除 `REFUND_PENDING / REFUNDING / REFUNDED` 不一致，让「退款中」tab 语义清晰。
- **改动点**：核对 `orders.applyRefund`、`adminOrders`、`payment` 退款相关状态，统一为「退款中 = REFUND_PENDING/REFUNDING，退款完成 = REFUNDED」，并同步前端 `OrderModel`。
- **依赖**：T2.4。
- **验收**：退款状态全链路取值一致，前端映射不再散落。
