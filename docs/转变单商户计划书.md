# 转变单商户计划书（多商户 → 平台唯一商户）

> 目标：把当前「多商户电商」改造成**单商户**——平台即唯一商户，全站只有两类角色：**管理员（admin）** 与 **买家（user）**。
> 约束（用户明确要求）：
> 1. 删除小程序的**商户端**，只保留 **user 买家端**；删除商户的 **web 端**，只保留 **管理员网页端 + 小程序 user 端**。
> 2. 修改代码完成「多商户 → 单商户」的完整转变：**分账逻辑、页面、以及其他所有涉及商户的逻辑**。
>
> 本计划按依赖关系做**拓扑排序**：决策 → 数据层 → 后端云函数（分账/订单/商品/支付）→ 管理端角色收敛 → 删除小程序商户端 → 删除商户 web 端 → 部署清理 → 回归。同一阶段内无强依赖的任务可并行。

## 一、关键设计决策（执行前需拍板）

> 这些决策决定后续所有改动的形态，先看这里。

### D1. 订单模型：彻底并单（推荐）vs 保留双表

**现状**：`orders`（支付主单）+ `merchant_orders`（按商家拆子单，买家/商家/后台都以子订单为准）。拆单是**为多商户独立履约/发货/退款**而设。

- **方案 A（推荐·彻底并单）**：删除 `merchant_orders`，全链路只保留 `orders` 一张订单表。买家 `list/detail/cancel/confirmReceive/applyRefund/review` 与后台发货/退款都直接操作 `orders`。理由：单商户无拆单需求，双表+拆单是最大的隐性复杂度来源，删掉后买家端、后台、支付回调、超时关单全部简化。
- **方案 B（保守·保留双表但单商户）**：保留 `merchant_orders`，但 `merchantId` 恒为 `null`（平台），不再按商家拆分（每支付单只产生一个子订单）。改动小、回归风险低，但留下大量死代码与「双表」心智负担。

> **本计划默认按方案 A 编写**；若你选择方案 B，则阶段 1/2/4/5 中所有「删除 `merchant_orders`」的条目改为「保留但收敛为单子订单」，其余删除项不变。

### D2. 商品审核工单：删除（推荐）vs 保留

**现状**：商家新增/改商品 → 提交 `product_audit_tickets` → 平台审核（填 `platformFee`）→ 通过才落库。而 SUPER_ADMIN 本就走「直接写库」分支（`adminProducts/index.js:488-490` 只有 `admin.merchantId` 非空才提交工单）。

- **推荐**：**删除审核工单链路**。单商户下「上传/下架/审核」都由管理员完成，管理员直接建/改商品（沿用现有 SUPER_ADMIN 直写路径）。删除 `submitTicket`、`listTickets`、`reviewTicket` 与 admin-web `AuditTickets.tsx` 页面。
- 备选：保留工单页面仅作「草稿箱」，成本高、无业务价值，不建议。

### D3. 平台抽成 `platformFee` 与商户号 `subMchId`（分账核心）

- **`platformFee`（平台抽成）**：单商户下平台=商户，不存在「平台向商家抽成」。**删除**该字段，买家实付价 = `sku.price`（`products/index.js:55-77`、`orders/index.js:161-162` 中 `+ platformFee` 全部去掉）。
- **`subMchId`（特约商户号/服务商分账）**：单商户走**直连**，钱直接进平台自己的 `WECHAT_PAY_MCH_ID`，无需服务商分账。**删除** `admins.subMchIdEnc` 及其加密存储、`setSubMchId`、`common/config.js:getWechatPayMerchantId` 里的 `SUB_MCH_ID` 分支、`common/commerce.js:cancelOrder` 里 `cloudPay.closeOrder({ subMchId })` 的 `subMchId` 参数。

### D4. 角色收敛

- 管理员账号**只保留 `SUPER_ADMIN`**（`admins.role` 不再有 `MERCHANT`）。`adminUsers.create` 默认 `role='ADMIN'` 可统一改为 `SUPER_ADMIN`（或直接去掉 role 入参，恒为超管）。删除所有 `merchantId` 字段/过滤。
- 小程序买家角色不变（`users` 集合，openid 维度）。

## 十一、风险与注意事项

1. **并单（D1=方案 A）是最大改动点**：`orders` 双表贯穿下单/支付/发货/退款/评价/超时关单六条链路，务必以 `orders` 为唯一事实源，一处一处替换，每改一处跑一次对应链路。
2. **`common/` 必须重新打包**：改 `cloudfunctions/common/*` 后不跑 `bundle-functions.js` 会导致云端缺模块。
3. **历史数据兼容**：已存在 `merchant_orders` / `platformFee` / `subMchIdEnc` 的旧数据需 T6.3 迁移，否则旧订单/旧商品残留商户字段但前端已不读，风险是「旧数据与旧契约脱节」。
4. **`devLogin` 随 `merchantAuth` 一并删除**：商户端登录绕行逻辑自然消失，无需单独处理（正是目标之一）。
5. **微信支付直连配置**：确认云环境已配 `WECHAT_PAY_MCH_ID`（平台直连商户号）而非服务商模式，`WECHAT_PAY_SUB_MCH_ID` 环境变量可移除。
6. **删除前先建备份/可回滚提交**：建议分阶段提交（数据层 / 后端 / 前端 / 清理各一个 commit），便于回退。
