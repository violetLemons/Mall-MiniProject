# 商户自营微信商城：功能盘点、同类对照与业务逻辑审查

审查日期：2026-10-09（Asia/Shanghai）。本轮依据当前代码，不沿用旧多商户文档结论。

## 0. 用户澄清后的适用性更新（2026-10-09）

用户确认每个商品仅一个SKU，无多规格；实际业务为公司自营水果。下面保留初版发现及复现证据，涉及多规格的原始结论不再作为当前整改依据，最新上线优先级见[上线流程与待完善清单](上线流程与待完善清单.md)。

- B01增加多规格选择器和B09尺码展示不适用，不增加这些功能；B08降为仅存在遗留SKU数据时的编辑风险。初版18项不能再直接表述为18项当前漏洞，其余15项仍需逐项整改或验证。
- B05价格与额度变化后的确认问题仍适用单SKU；B10指11种不同商品超过每单10种，不是要求多规格。
- R1完成单不自动退款的边界保留，但需有质量问题人工售后。已发货强制退回的规则应根据水果坏果、破损等场景重新确认，不能让客服假勾“已退货”绕过。
- 发现额外上线适配事项：页面七天无理由/吊牌承诺、公司资质公示、配送范围、生产秘密配置；示例苹果仍有两个ACTIVE SKU，需按单SKU业务修订种子和服务端校验，而不是恢复多规格UI。
- 本次复跑既有node scripts/run-tests.js仍36/36通过；未重跑初版10探针、未修改业务代码或连接真实微信资金接口。初版涉及多SKU的探针保留为历史证据，不算当前业务的验收。

## 1. 主要发现

初版列出18项候选实现问题或用户流程错误，其中B01–B06为当时的优先建议；该计数和多规格建议已被第0节适用性更新覆盖。另有6项需要确认的业务政策及运营缺口，不能混算为已证实漏洞。初版未发现新的、经该轮复现的任意提现或支付金额篡改漏洞。

实际运行现有测试：36/36通过。新增10个隔离探针均观察到预期的异常行为。探针“通过”表示成功复现问题，不表示问题已经修复；部分探针验证底层行为，前端弱网、重开页面等完整场景依据调用链推导。未改生产业务源码，未连接云数据库或真实支付，未部署。

严重性：P1表示会影响主要购买、资金处理或持续运行；P2表示特定边界或管理、体验错误。严重性是本次工程判断，不是竞品评分。

### 2.3 状态、资金和范围

- 正常：PENDING_PAYMENT → PAID → SHIPPED → COMPLETED。
- 取消：PENDING_PAYMENT → CLOSING → CANCELLED；可信支付证据可将CLOSING转回PAID。
- 退款：PAID/SHIPPED → REFUND_PENDING → REFUNDING → REFUNDED；拒绝恢复申请前状态。
- 下单时扣购物额度；未付款取消返额度；退款成功返额度；微信现金按payAmount退款，不按商品总额退款。
- 单主单不等于单账本：支付、退款、额度流水仍独立保留。客户端单价不作为结算依据。
- 已确认主动精简：单商户、无库存、无自提、无抽成分账、无商户工单；这些不计为漏洞。

## 4. 实现问题清单

### B01 [P1] 多规格商品实际只能买首个SKU，显示价还可能对应另一个SKU

适用性更正：仅一个SKU时原多规格购买场景不适用；以下保留初版复现，不按其建议增加选择器。单SKU种子及约束另见上线清单C09。

位置：miniprogram/pages/goods/detail/index.ts:95、101、130；同目录index.wxml没有挂载sku-popup；products/index.js:210按规格升序返回SKU。

触发：商品有两个颜色/尺码，首SKU2000分、另一个1000分。详情展示product.price最低价1000分，按钮直接取skus[0]，结算缓存仍1000分，后端收取所选首SKU真实价2000分。其他SKU没有正常选择入口。

影响：选错规格、错误价格预期，后续发货/退款争议。探针通过实际编译页面方法确认首SKU、旧显示价和未打开弹层。

建议：单一默认SKU才直达；多SKU显示选择器，确认时使用所选SKU的价格/图片/规格。恢复前端数量选择也应与后台一致。

### B02 [P1] 异常关单会反复占据批次，且可耗尽收货/退款巡检时间

位置：cloudfunctions/orderTimeoutJob/index.js:5、6、7、10、12。

触发：最早30张到期单持续查单失败，永远保持CLOSING；任务始终按expireAt取相同30张，没有lastCheckedAt、退避或游标。第31张可以正常取消的订单连续两轮也不会处理。探针已复现。

同时三类任务共用30秒deadline；前面几次10秒微信超时就可能持续让后面的发货、退款轮询没有执行机会。此时间预算结论为调用链分析，未执行真实超时。

影响：后来订单额度不能及时返还；已支付订单/退款状态迟迟不更新。建议给各类任务独立预算，异常单按nextCheckAt退避，按最后检查时间公平调度；不能跳过真实资金核验直接取消。

### B03 [P1] 微信退款尚未创建成功，本地已永久进入“退款中”，定时任务不能自动恢复

位置：adminOrders/index.js:8、14；commerce.js:210；orderTimeoutJob/index.js:12；admin-web/src/pages/Orders.tsx:58。

触发：beginRefund先落REFUNDING/PROCESSING，随后微信查询不存在、创建被拒绝或外部调用失败。任务只queryRefund，不处理RESOURCE_NOT_EXISTS重新申请；它也不区分未创建、微信处理中和明确失败。探针模拟拒绝后确认订单保持REFUNDING且巡检没有创建动作。

后台“查单后重试”可人工再次创建尚未存在的同号退款，因此不是绝对无法恢复；但若微信已返回CLOSED/ABNORMAL，同号查询只返回该终态，现有入口没有后续恢复流程。

建议：记录申请发送/未知/处理中/明确失败状态、错误原因和下次核验时间；未创建退款在核实后按原号重试；官方终态失败需要有证据的人工恢复流程。必须保持退款幂等，不可盲目换号重复发钱。

### B04 [P1] 下单幂等标识只存在页面内，弱网后重开会生成重复业务订单

位置：miniprogram/pages/checkout/index.ts:67、433；services/order.service.ts:69；commerce.js:83。

触发：立即购买下单云端成功，响应丢失，页面仍有结算缓存；用户返回并重新进入，onLoad生成新requestId，同一购买再下单。服务端只防相同requestId，新的标识会再建单和扣额度。探针确认同内容不同标识形成两单；完整弱网重开场景由前端生命周期推导。

购物车订单可能因原cartId已扣完而拒绝第二次，不应宣称所有结算都必定重复；立即购买不带cartId是明确受影响场景。

建议：为一次结算意图持久化requestId和输入指纹，未知结果先查询/恢复已有订单；用户明确新购或改变输入再更新标识。

### B05 [P1] 结算显示金额与服务端实际金额变化时，未重新确认就直接调支付

位置：checkout/index.ts:88、433、461；commerce.js:99、107。

触发：用户保留旧价格/旧额度页面，期间商品涨价或额度在另一单消耗。服务端按最新数据下单，但前端不更新返回totalAmount/balanceAmount/payAmount，也不让用户确认变化，直接payOrder。B01更容易触发这一问题。

这是确认流程缺失，不是客户端能篡改服务端价。建议提交前权威报价，差异需用户确认；付款时以已创建订单快照为准，不重新计算历史订单价格。

### B06 [P1] 商品保存与审核任务分属两次事务，队列失败会留下无人处理的待审商品

位置：adminProducts/index.js:266、322；common/catalogSafety.js:32、44；auth/index.js:updateProfile；contentSafety.js:9。

触发：主体保存成功、下架并写PENDING，随后审核队列事务失败或进程终止。主数据已提交，但没有该版本content_reviews；contentReviewJob只扫描队列，无法发现这个商品。探针注入队列写失败已复现商品下架/PENDING且队列为空。

分类/轮播/头像采用同类“先主实体后任务”模式，也应覆盖。建议实体版本和任务槽位同事务落库，或使用可恢复的持久化待办及孤儿扫描；客户端保存失败不能掩盖已部分保存。

### B07 [P2] 账户余额上限与返还额度共用，会阻塞取消甚至已到账的现金退款落账

位置：commerce.js:9、66、183、239。

触发：原订单扣额度后，用户再兑换卡密至余额上限100000000分（100万元），原订单取消/退款需要返额度，before+delta超上限。取消探针确认INVALID_PARAMS且保留CLOSING。混合支付退款则存在现金已由微信退款成功、额度返还失败导致本地无法终结的路径，未实测真实微信。

建议额度发放上限计入已占用且可能返还的额度，或允许退款/解冻返还突破发放限额并完整记账；不可让资金凭证因余额展示上限永久落不了账。这是大额边界，实际低额度经营发生率较低。

### B08 [P2] 废弃SKU累计超过30条后，商品常规编辑也被拒绝

适用性更正：无多规格业务时仅为遗留数据风险，不是正常单SKU经营必然出现的问题。

位置：adminProducts/index.js:150、173、301。

规格更新保留旧SKU为DISABLED，但上限检查把所有历史SKU算入old.length；普通编辑又把所有旧SKU作为inputs。累计31条历史规格，即使只有1条在售，也不能正常保存。探针已复现。

建议在售规格上限与历史快照保留分开；不得靠物理删除订单引用SKU解围。

### B09 [P2] 后台发货详情漏显示商品尺码/规格

适用性更正：当前无尺码/多规格，原结论不适用；水果每份净重等静态商品描述另按实际业务完善。

位置：admin-web/src/pages/Orders.tsx:46。类型和API映射保留i.size，但视图只显示商品名、colorName和count。

同名同色不同尺码时，管理员发货弹窗难以区分。建议显示完整规格，特别是多SKU选购修复后；这是可直接从模板确定的遗漏。

### B10 [P2] 购物车允许100款并全选，结算单却最多10款且没有提前处理

位置：cart/index.js:addCart；miniprogram/pages/cart/index.ts:onCheckout；commerce.js:73。

勾选11款仍进入确认页，提交才整体拒绝。探针验证后端11款拒绝；前端没有限制或拆分引导。建议明确每单上限并在结算前提示或由用户分批选择；不自动拆为多笔现金支付。

### B11 [P2] 已选收货地址可能在结算页再次显示时被自动换回默认地址

位置：checkout/index.ts:83、133、186。

地址数为2及以上，applyAddressRules优先默认而不是当前selectedAddressId；onShow会重跑该规则。用户手动选B、页面恢复后可能又选A。新地址保存中也以默认优先规则初始化。

建议初次进入才应用默认，恢复时保留仍有效的当前选择；最终下单前展示实际使用地址。此项为生命周期静态分析，需要微信真机验证外部唤回行为。

### B12 [P2] 图片审核暂时超时会变成永久FAILED，没有同版本自动重试

位置：contentSafety.js:12、34；contentReviewJob/index.js。

processPending只扫描REQUESTING；所有异常（包括临时网络故障）都写FAILED。探针连续跑两次只调用微信一次，任务保持FAILED。提交已成功却本地保存traceId失败还有结果无法关联风险。

建议区分暂时失败与内容拒绝，持久化退避/次数/最后错误；同版本未绑定结果须有核验和补偿流程，不把失败自动PASS。

### B13 [P2] 提示用户刷新详情确认支付，但详情读取没有触发支付查单

位置：services/order.service.ts:98及payOrder末尾；pages/order/detail/index.ts:loadOrder；cloudfunctions/orders/index.js:detail；payment/index.js:queryOrder。

通知延迟/失败且首次queryOrder未成功时，详情仅orders.detail读本地；它也没有onShow刷新或轮询。再点付款可被已过期状态拒绝，支付补偿要等通知或超时巡检，提示的刷新未必能解决。

建议待确认付款的详情使用受限queryOrder并刷新权威状态，页面恢复时核验，避免重复调支付。不可把wx.requestPayment成功直接写PAID。

### B14 [P2] 后台商品接口固定只取第一页50条，后续商品没有分页管理入口

位置：admin-web/src/api/client.ts:129、133；pages/Products.tsx:loadProducts。

服务端有分页/total，但封装固定page=1/pageSize=50，只返回数组，页面不能浏览第51条之后的默认列表。搜索部分可找回不等于完整管理。建议传页码并返回total，后台完整分页；Dashboard最近50单已经明确说明，未将其当全量统计漏洞。

### B15 [P2] 后台维护的详情长图未用于买家商品详情

位置：products/index.js:71；pages/goods/detail/index.wxml“细节图片”循环。

API有detailImages，后台维护该字段，买家详情却再次循环product.images，导致真正的参数/售后说明长图可能不展示。模板另硬编码“配备独立吊牌与溯源码”，无对应商品能力判断。

建议主轮播与详情长图分别渲染，商品承诺由实际商品数据决定。

### B16 [P2] 收藏、浏览历史、消息开关、退出/切换账号包含无效交互

位置：goods/detail/index.ts:75；profile/index.ts:106、115、783、792；profile/index.wxml:437。

- 收藏只修改当前详情data，没有写个人页读取的sneaker_mall_favorites，离开即消失。
- 浏览历史只有读取/清空，本轮检索没有商品浏览写入路径。
- 消息开关只修改data并提示已开启/关闭，没有持久化偏好或订阅请求。
- “退出登录/切换账号”只有Toast及关闭抽屉，没有清用户缓存或改变登录状态；微信OPENID本身不可由该按钮切换。

建议实现有实际效果的对应流程；微信身份下准确命名退出本地资料显示等动作，无法提供的功能应收敛入口。

### B17 [P2] 商品公开文字安全校验遗漏品牌和规格名称

位置：adminProducts/index.js:264、153、163；products/index.js:232；goods/detail/index.wxml品牌。

校验聚合name/subtitle/description/tags，未包含brand和skus.colorName；updateSkus也没有审SKU公开文字。品牌和颜色名可进入公开商品、购物车、订单显示。

建议按实际将发布的规范化字段完整检查，再提交同版本图片队列。本轮确认字段覆盖缺失，未向真实微信发送违规内容。

### B18 [P2] 登录节流同时计算成功请求，可被针对用户名阻断正常管理

位置：adminAuth/index.js:13–19。

任何调用先加用户名计数，正确登录也耗费次数；10次成功后第11次正确密码仍RATE_LIMITED，探针已复现。攻击者知道用户名也可反复发请求占满该账号窗口，影响后台售后和发货。

建议区分失败计数、请求频率与可信已认证会话，结合来源限流/验证机制；保留防暴力破解，不能简单取消节流。

## 5. 业务政策与功能缺口（不算上述18项实现问题）

| 编号 | 当前规则或缺口 | 经营影响与待决策内容 |
| --- | --- | --- |
| R1 收货后售后 | COMPLETED彻底拒绝退款，未设置售后申请截止时间，也无商家主动发起退款入口 | 已确认“完成单不自动退款”应保留，但不等于收货后没有人工售后；需要明确人工申请/审批/留痕/资金处理通道。不得自动恢复无限退款 |
| R2 退货管理 | 没有撤销申请、退货批准、退货地址、买家寄回运单、退货证据、拒绝理由详情和超期处理 | 一次申请直接阻止发货/收货；误申请不能自行撤回，整单退款须外部客服串联。参考S3–S5设计最小闭环 |
| R3 额度政策 | 默认强制优先抵扣，可100%抵扣；前端没有useBalance选项；卡密兑换后不保存额度有效期/批次归属 | 需明确额度是赠送权益还是其他来源、是否限比例/品类/有效期；卡密截止日仅限制兑换，不限制已兑换额度消费。若希望额度到期或比例限制，目前无法执行 |
| R4 限购/履约能力 | 每SKU每单5件、无跨单额度/购买次数、无下单频率、无配送区域校验和发货时限 | “单款限购5双”文案和每人限购不是同一规则；无库存已主动选择，但仍须明确供货能力、无法履约如何主动退款、免费配送范围 |
| R5 财务运营 | 有流水集合但没有账务查询/异常待办/退款失败告警/每日对账后台；纯余额单仅本地物流 | 不能依赖最近50单看板核对总账；支付退款异常须可发现、分配和处理。全额度单无微信现金交易号的边界已确认，非伪造交易号解决 |
| R6 内容与营销 | 无完整优惠券、收藏云同步、会员权益、商品评价展示；广告关闭、专区前端隐藏；后台统一价格会覆盖不同SKU价格 | 有些是合理首版取舍，但后台应明确哪些内容可实际展示。多SKU差异价格和“保存基准价作用全部规格”是已有约定，需评估运营是否接受，不将该已确认策略直接说成新漏洞 |

其他需定向验证的风险：分类删除的引用检查与删除没有在一个事务内，多管理员并发新增子类/商品可能形成孤儿引用；外部HTTPS图片允许使用同一URL更换内容，审核结果无法保证之后仍是同一资源；审核PENDING缺少丢失回调的长期恢复路径；后台审批证据与实际动作日志尚不完整。这些不计入已复现探针数，应有单独故障/并发验证后决定整改优先级。

## 6. 建议处理顺序及验收

本节保存初版建议；多SKU选购/尺码用例不再执行，当前顺序及验收以第0节和《上线流程与待完善清单》第4至6节为准。

1. 先处理B01/B05：多SKU正确选购、选中规格价格和权威结算金额一致；后台显示完整规格。
2. 处理B02/B03/B07/B13：关单公平巡检、失败退款可恢复、额度返还边界、买家主动支付核验。分别模拟未知、明确失败、重复成功和并发，任何恢复都不能重复返款。
3. 处理B04/B06/B12：持久化一次购买意图，审核主体与队列原子或可恢复；故障后可找到并继续原业务。
4. 处理B08–B18其余项；确认R1–R6再实现业务扩展，避免把对照平台的功能全部搬入。
5. 使用实际CloudBase做事务/索引/并发验证，微信体验版走真实小额支付、退款、发货、收货和审核消息。内存适配器事务串行，不证明云并发正确。

重点验收：两种不同价格/尺码买对SKU；网络断在下单成功后不重复建单；30个失败关单不堵后续；退款未创建可按原号恢复；现金已退款额度返还可落账；队列写失败/暂时超时可恢复；31条历史SKU可编辑；11款结算得到明确提示；返回结算不改地址；第51条商品能管理；收藏和设置执行真实动作。

本轮复现命令（仓库根目录）：

```powershell
node scripts/run-tests.js
node work/business-audit/probes.cjs
```

探针复用本地适配器和真实函数入口，用stub替代微信接口；所有数据仅在进程内，运行结束即丢弃。两项页面/请求标识探针与后端约束探针需要结合源码理解，不能宣称为完整真机端到端测试。
